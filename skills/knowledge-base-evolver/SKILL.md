# 知识库自进化管家

让知识库形成"输入→消化→归档→索引→可复用"的闭环。适用于任何 Markdown 知识库（Obsidian 等）。

开工前先确认三件事：
1. 收件箱目录在哪（如 `00_收件箱/` 或用户指定）
2. 已整理区目录结构是什么（按主题分类的目录树）
3. 有没有索引文件（MOC / Map of Content / Wiki / 目录页）

没有索引体系时，先帮用户搭最小骨架（见 `@references/setup-guide.md`），再开始消化。

## 核心流程：收件箱消化六步

对收件箱里的每一个文件执行：

### 第 1 步：通读与四步分析

对每份待处理内容做四项分析，写成摘要附在笔记顶部：
1. **摘要**：这份内容讲了什么（3-5 句）
2. **用途**：对知识库主人有什么价值
3. **使用场景**：什么时候会回头查它
4. **推荐动作**：归档到哪里 / 与哪篇合并 / 建议如何使用

### 第 2 步：查重

- 检索已整理区，找同主题已有文件
- 关键词搜索 + 索引文件浏览双管齐下
- 判定三种结果：全新主题（新建）/ 同主题（合并）/ 已覆盖（不重复入库，在原文标注出处即可）

### 第 3 步：合并（同主题时）

- 同主题内容**只保留一个主文件**
- 新内容的增量信息合并进主文件，标注来源和日期
- 合并后删除重复文件（移动到回收站或用户确认后删除）
- **不删文件内容中的原始观点**，只做结构合并

### 第 4 步：归档移动

- 按内容类型移动到对应分类目录
- 文件移动后，旧位置不留副本
- 清理移动后产生的空目录
- 未处理完的内容不能留在收件箱伪装成已消化——宁可标记"待定"也不要乱归档

### 第 5 步：索引同步（不可跳过）

每新增、移动、删除一个文件，必须同步更新：
- 该文件所在**最深层目录的 MOC**（同级同名 .md 索引）：新增 → 追加一行 `- [[文件名]] — 一句话说明`；移动 → 旧 MOC 删除、新 MOC 追加；删除 → 移除对应行
- 顶层索引/Wiki：语义标签与路径的映射表同步
- frontmatter 的 `updated` 字段更新为今天

### 第 6 步：变更日志收尾

每次批量操作后，在变更日志（如 `变更日志/YYYY-MM.md`）追加一条：

```markdown
## YYYY-MM-DD HH:mm
- 动作类型：新增 / 修改 / 归档 / 合并 / 删除 / 重命名
- 摘要：一句话说明
- 影响文件：[[文件A]] [[文件B]]
- 后续确认：无 / 待用户确认事项
```

## 执行纪律

- **只增不删原则**：默认不删除任何用户内容；删除仅限"合并后确认重复"且先征得同意
- **不确定就问**：主题归属模糊、分类树没有对应目录时，先问用户，不要自作主张乱放
- **批量上限**：一次消化超过 20 个文件时，先给用户一份消化方案清单（每个文件去哪、合并到哪），确认后再执行
- **时间戳**：新建文件 frontmatter 写 `created` + `updated`；实质修改更新 `updated`
- **双链优先**：关联内容用 `[[双链]]` 连接，不复制已有内容

## 快速模式

用户只是随手丢来一篇新资料（非批量）：跳过方案确认，直接执行 1→2→4→5→6，最后用两句话汇报"放哪了、和什么有关"。

## 例外情况

- 收件箱里有**笔记同步工具/外部应用**自动生成的子目录：也算待处理内容，一并消化；消化后只清理空目录，不动非空目录
- 遇到敏感信息（密码/Token/手机号）：归档前提醒用户，建议移到私密区，不写进索引摘要
